# Data sources and provenance

- Discovery attempt (2026-11-01, from the build sandbox, one `GetCapabilities` request per endpoint, short timeout, TLS verification on): all three closed the connection (`Connection reset by peer`). No retries were made. **Layer names, CRS, GSD (the ~7 cm figure is unverified), WFS availability and redistribution terms remain unknown.** No Quito data is bundled.
- WMS images are rendered pictures, never cadastral vector data, and a small WMS crop does not retain the drone GSD.
- To use them: verify permissions with the owner, read `GetCapabilities` yourself, and pass downloaded GeoTIFF/GeoPackage files to the CLI.

## Interactive WMS access
- **Streamlit tab "Mapa WMS (cualquier servicio)"**: type any https WMS URL (the IGM Ecuador orthophoto WMS `https://www.geoportaligm.gob.ec/orto/igm/wms` is the default, with the 2022 and UAV services as further examples; both were supplied by a user and not verified by the maintainers), load its layers live from `GetCapabilities`, click the map to place the red square (a small coverage gets a square preselected at its centre), choose its size (80-260 m, enforced), and the app downloads **only that area** (one `GetMap`, at most 512 px) and runs inference on it. The map shows the extent the layer declares and zooms to it; areas outside it are blocked, and an empty image (transparent, black or white) is reported with its likely cause (no data there, typical of UAV flights that cover specific zones).
- The comparison with cadastral vectors is done outside the tab: download the candidate footprints (GeoJSON, georeferenced) and compare with `qbl compare` / `qbl run --reference`. The CLI (`qbl fetch-area`) can also fetch polygons from a WFS; this was tested only against a simulated service.
- Tested only against a simulated WMS. A user reported an empty image for the IGM UAV layer on an area chosen before coverage checks existed; the real services could not be queried from the development environment.
- The image georeferencing comes solely from the requested bbox + CRS (WMS 1.3.0 axis order handled). A WMS image is a rendered view, **not** original orthophoto pixels; its GSD is the request grid, not the source GSD.
- GetMap is requested the way web maps do: as 256 × 256 px tiles (at most 4 requests for a 512 px image) that are stitched together, because some services fail on other request sizes (a server-side `NullPointerException` was reported on a single 512 px request in all CRS while the browser's 256 px tiles worked; the cause on that server is not confirmed). The CLI can still ask for a single request (`tile_size=None` in the API). The app also has a diagnostic button that sends at most 5 test requests (256 and 512 px, with/without transparency, JPEG, another CRS) and reports which ones the service accepts.
- The CRS is Web Mercator (EPSG:3857) first, because that is what web maps request. If the service answers with an error (for example a server-side `NullPointerException`), up to two more requests are tried in other CRS (UTM 17S, then WGS 84) and the app shows every attempt with its URL. Image sizes and areas are always computed in true ground metres, whatever the request CRS. The layer's declared scale limits, when present, are shown, because outside them a server draws nothing.
- Browser download path: some services answer the user's browser (the map overlay works) but fail every GetMap sent by the server running the app (reported for the IGM services: a `NullPointerException` for every size, format and CRS tried, while the same layer draws in the browser; the cause is unknown and the app does not imitate a browser to get around it). The app then offers a link to a single 256 × 256 px GetMap image of the square for the user to open and save, and georeferences the uploaded file with the bbox and CRS of that request, rejecting a file of any other pixel size.
- Map display: the layer overlay requests tiles up to the layer's native zoom (19, about 0.3 m/px at the equator, or less if the layer declares a `MinScaleDenominator`) and enlarges them beyond it; the map tab has a "Detalle máximo del mapa" slider to lower that level when a service stops drawing earlier (a user reported the IGM layer vanishing at a scale bar of 50 m with level 19). Without this the overlay vanished when zooming in past a scale bar of about 10 m (reported with the IGM service; reproduced with a simulated server that refuses finer detail).
- No crawling: a normal download is at most 4 tile requests; when the service fails, a CRS that fails on its first tile costs one request (at most 3 CRS); no other retries, TLS verification always on, https only, hosts resolving to non-public addresses refused, redirects refused, response size capped.
- Check the data owner's terms before reusing downloaded imagery.

## Bundled demo (`examples/demo/`)
- `vegas_sn2_img10_rgb8.{tif,png}`: 512×512 crop of SpaceNet-2 AOI_2_Vegas image `img10` (pan-sharpened RGB, EPSG:4326, stored 8-bit after 0.5–99.5 percentile stretch per band). **Not Quito.** CC BY-SA 4.0, © SpaceNet / Maxar (source: `s3://spacenet-dataset/spacenet/SN2_buildings/train/AOI_2_Vegas/`). Acquisition date not recorded here.
- `vegas_sn2_img10_reference_buildings.geojson`: the 20 SpaceNet-2 building polygons intersecting the crop, clipped. They are building-footprint annotations of that dataset, used as *illustrative reference*; they are neither Quito cadastre nor an independent re-review.
- Demo choice reason: a Quito sample could not be obtained/redistributed (see above) and an openly licensed aerial dataset was available.

## Synthetic fixtures
`tests/conftest.py` generates deterministic synthetic scenes in EPSG:32717 (UTM 17S); coordinates are arbitrary test values, not real places.
